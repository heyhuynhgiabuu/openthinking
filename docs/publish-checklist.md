# Publish Checklist

Use this checklist before publishing OpenThinking publicly.

## 1. Product clarity

- [ ] README clearly explains what OpenThinking is
- [ ] README clearly explains what OpenThinking is not
- [ ] repo promise is narrow and specific
- [ ] no vague "founder copilot" or "AI for everything" language remains

## 2. Skill quality

- [ ] every public skill has a `SKILL.md` with valid YAML frontmatter
- [ ] every skill has `examples.md`
- [ ] every skill has `eval.md`
- [ ] every skill solves one clear decision problem
- [ ] overlapping or redundant skills are removed
- [ ] weak or generic wording is tightened

## 3. Example quality

- [ ] first three skills have worked examples with real judgment
- [ ] remaining skills also have non-placeholder examples
- [ ] one end-to-end worked flow exists
- [ ] examples show blunt recommendations, not motivational fluff

## 4. Installability

- [ ] local `npx skills add . --list` works
- [ ] all intended skills are discoverable
- [ ] no malformed YAML frontmatter remains
- [ ] install instructions in README are accurate

## 5. GitHub readiness

- [ ] repo name and description are sharp
- [ ] README opening section is strong enough for a first-time visitor
- [ ] docs folder is easy to navigate
- [ ] license is chosen and added
- [ ] initial topics/tags are planned for GitHub

## 6. Scope discipline

- [ ] no extra half-finished skills are included
- [ ] no app/platform scaffolding distracts from the skill library
- [ ] no marketplace or ecosystem claims are made
- [ ] packaging stays narrow and easy to adopt

## 7. Launch plan

- [ ] decide what is free now
- [ ] decide what remains future/pro tier later
- [ ] publish 1-3 short posts showing real examples
- [ ] share one install command, not a complicated onboarding story
- [ ] collect feedback on repeated use, not just compliments

## 8. Kill signals after launch

Watch for these warning signs:
- people praise the idea but do not install
- people install one skill but never use a second one
- users copy outputs once and never return
- the repo feels like content, not a usable tool
- requests pull the project toward a broad founder OS
